# 0.29.0 预开发计划：YSM 特殊投射物弹幕

> 状态：预开发设计，API、字段名和性能上限均未冻结。
> 目的：把少量关键弹幕交给 OpenYSM（以下简称 YSM）使用自定义模型渲染，改善
> `kunai`、`knife` 等非 Billboard 弹幕的辨识度和风格统一性，同时保留 YH
> 批处理弹幕的吞吐量。

## 1. 背景与问题

YH 的普通弹幕是虚拟的 `SimplifiedProjectile`，由客户端弹幕缓存和
`ProjectileRenderHelper` 批量绘制，不经过 Minecraft 普通的
`EntityRenderDispatcher`。这条路径适合大量弹幕，但目前 `KUNAI`、`KNIFE` 等类型
主要使用互相垂直的面片，单颗约八个顶点，成本低却容易出现辨识度不足、风格不统一的问题。
`TALISMAN`、`SCALE`、`KUNAI`、`KNIFE` 当前分别落到 Swinging、特殊 Swinging
和 Cross 等多个渲染类型，尺寸、染色和贴图规则也散落在各自分支中，难以作为统一的
实验入口。

YSM 的投射物模型管线则以真实的 Minecraft `Projectile` 和
`ProjectileCapability` 为入口，不能直接接收 YH 的虚拟弹幕。YSM 模型即使完成几何
预烘焙，仍需要逐实体处理动画、骨骼和绘制调用；GPU、Native/SIMD 和 Compatibility
路径的成本也不同。因此本计划定位为“少量特殊弹幕的表现层”，不改变 YH 的大规模
弹幕模拟和批处理主路径。

现有 Shooter 已经是真实的 YH `LivingEntity`，并通过 `ShooterRenderer` 调用
`YSMClientCompat.delegateRender`。它可以继续使用现有 YH→YSM LivingEntity 管线，
与本计划的投射物通道分开评估。以用户提供的模型包
`D:\IdeaProjects\MC模组\资源\剑圣魂魄妖梦_1.0_pro` 为例，`main.json`
约有 239 个骨骼、582 个立方体和约 13,968 个顶点；`arrow.json` 约 480 个顶点，
`trident.json` 约 576 个顶点。少量 Shooter 使用 `main.json` 风险可控，但仍需实机
确认玩家专属 MoLang 和动作是否适用于该实体。

## 2. 目标

1. 允许符卡创建者显式指定少量弹幕使用 YSM 投射物模型，并为每个发射动作保留 YH
   回退路径。
2. 将 `kunai`、`knife`、`scale`、`talisman` 四项收束为新的实验性 `custom`
   弹幕类型；四项原有外观作为迁移期变体，不再继续扩展四套独立的 YSM 接入逻辑，
   并在清理引用后预备删除旧类型。
3. 让 `custom` 统一承载 YSM 投射物模型、尺寸调整、染色/白色叠层和 YH 回退外观，
   作为渲染层调试和风格探索入口。
4. 通过 Editor/Analyzer 提示逐实体渲染的性能成本，由符卡创建者手动确认后才能
   认证或标记为已确认。
5. 隔离 Boss、Shooter 和弹幕三种模型作用域，避免当前 Boss 模型与符卡 action
   模型绑定互相覆盖。
6. 保持 OYSM/YSM 为软依赖：未安装、API 不兼容或模型缺失时，只回退受影响的弹幕，
   不影响 Boss、符卡逻辑和普通弹幕。

## 3. 非目标

- 不把所有 YH 弹幕改造成真实 Minecraft 实体。
- 不用 YSM 替换 YH 的大规模弹幕批处理器、碰撞、擦弹或服务端状态机。
- 四项旧类型属于预备删除项；不把它们当作需要长期兼容的公开 API。删除前仍需完成
  源码引用、数据定义和编辑器选项的清理，避免遗留的符卡或序列化入口静默失效。
- 不默认从 Boss 当前模型推导弹幕模型，也不把 `SpellDefinition.display.model_id`
  直接复用为弹幕模型字段。
- 不修改 OYSM/YSM 第三方源码；任何兼容均通过 YH 自有反射、事件或适配层完成。
- 不在预开发阶段承诺固定的 `kunai`/`knife` 资源格式、固定顶点数或固定实体上限。

## 4. 当前架构证据与接入边界

### 4.1 YH 弹幕

普通弹幕的权威位置仍在服务端，客户端只接收并表现同步结果。YH 客户端缓存中的
`SimplifiedProjectile` 没有可直接传给现有 YSM Projectile 管线的真实实体身份。
因此首选接入形态是新增一个“虚拟投射物渲染桥”：桥接层接收 YH 弹幕的姿态、位置、
旋转、贴图和模型槽位，调用 YSM 的投射物模型绘制能力；桥接失败时回到现有
`ProjectileRenderHelper`。

如果当前 YSM 版本没有可用的虚拟投射物入口，备选是为极少量特殊弹幕建立真实
`Projectile` 的视觉通道，并让服务端弹幕状态继续由 YH 管理。该通道必须限制在
显式启用的 action 内，不能把所有弹幕实体化。

### 4.2 Shooter 与 Boss

- Boss 当前模型只影响 Boss 本体。
- `SpawnShooterAction.ysm_model` 只影响 Shooter。
- `fire_danmaku` 的投射物模型只影响该 action 产生的弹幕。
- Shooter 可以复用现有 LivingEntity 委托，不应借用投射物槽位。

生成弹幕时应解析并快照模型来源；弹幕飞行期间 Boss 切换模型，不追溯修改已经生成
的弹幕。模型、贴图或 YSM 能力缺失时，只让该弹幕回退到 YH 路径。

### 4.3 实验性 `custom` 弹幕类型

`custom` 是新的渲染/数据类型，首期只接管以下四个现有外观：

实现上优先把 `CUSTOM` 作为新的逻辑类型和统一配置入口；旧四项只在迁移阶段作为
临时变体或转换源存在，完成源码引用、数据定义和编辑器选项清理后删除。当前
`YHDanmaku.Bullet` 的物品表按枚举序号注册，因此删除动作应作为一次明确的注册表和
资源清理变更执行，而不是留下长期的空壳枚举项。按当前产品判断，四项没有需要继续
维护的事实性下游符卡应用，不为它们设计长期存档兼容层。

| 迁移变体 | 当前 YH 外观 | `custom` 的首期回退实现 |
| --- | --- | --- |
| `kunai` | Cross 面片 | `LayeredCrossProjectileType` 或 `CrossProjectileType` |
| `knife` | Cross 面片 | `LayeredCrossProjectileType` 或 `CrossProjectileType` |
| `scale` | 带倾角的 Swinging 面片 | `SwingingProjectileType` 的对应参数 |
| `talisman` | Swinging 面片 | `LayeredSwingingProjectileType` 或 `SwingingProjectileType` |

这里的“合并”首先是渲染抽象和数据语义的合并：符卡和渲染器面向
`custom + variant`，不再为四项各自增加 YSM 分支。迁移期可以把旧值转换成对应的
`custom` 变体；清理完成后，旧物品注册名、标签和旧类型分支一并删除，不为没有实际
下游应用的四项建立长期兼容层。

`custom` 的表现参数分为三层：

1. **变体默认值**：决定无 YSM 时使用哪一种 YH 几何、默认透明度和默认尺寸；
2. **`base_scale`**：弹幕的基底尺寸，影响模型最终大小、碰撞/判定箱、视角剔除和
   其他依赖实体尺寸的逻辑；它属于弹幕实例/物理表现层，不能被 YSM 模型单独覆盖；
3. **`model_scale`**：仅作用于模型局部变换，影响模型显示大小，不改变碰撞箱、判定
   箱、视角剔除或服务端运动；最终视觉尺寸通常为 `base_scale × model_scale`；
4. **action/YSM 覆盖值**：由 `fire_danmaku` 显式选择模型槽位、`model_scale` 和是否
   进入 YSM 路径。覆盖值只影响渲染，不改写 `custom` 的伤害、碰撞或飞行轨迹。

其中 `base_scale` 必须沿用弹幕实体的权威同步和判定链；`model_scale` 可以只存在于
客户端表现配置，但必须由符卡定义或已同步的 action 配置确定，不能由客户端模型文件
自行改变。

因此同一个 `custom` 变体可以先用 YH 几何快速调试，也可以在少量实例上切换到 YSM
模型；YSM 缺失时仍能得到与旧四项接近的外观。

## 5. 弹幕选择粒度与配置草案

首期采用 **action 级选择**：一个 `fire_danmaku` action 的全部发射物共享同一套
YSM 投射物配置。需要混用时拆成两个 action，不按弹幕序号或单颗弹幕保存配置，
以免数据量、编辑器复杂度和运行时分支迅速膨胀。

以下仅为 schema 草案，字段名和枚举值未冻结：

```json
{
  "type": "custom",
  "variant": "kunai",
  "base_scale": 1.0,
  "tint": {
    "mode": "danmaku"
  },
  "ysm_projectile": {
    "model_source": "fixed",
    "model": "妖梦模型ID",
    "slot": "kunai",
    "model_scale": 1.0,
    "max_instances": 8,
    "fallback": "yh",
    "acknowledge_cost": true
  }
}
```

建议语义：

- `type: custom`：选择实验性统一类型；首期不改变运动、碰撞和伤害语义；
- `variant`：`kunai`、`knife`、`scale`、`talisman`，用于选择 YH 回退几何和默认表现；
- `base_scale`：基底尺寸乘数；提高它会同时影响模型大小、碰撞/判定箱和视角剔除等
  实体尺寸相关行为；需要与现有 `danmaku.scale()` 的权威语义对齐，不能再产生第二套
  物理尺寸；
- `tint.mode`：沿用现有染色/白色叠层语义，至少支持 `danmaku`、`fixed` 和关闭叠层；
- `model_source: none`（缺省）：完全使用 YH 几何/渲染路径；
- `model_source: fixed`：action 明确指定模型包或模型 ID；
- `model_source: boss_current`：生成时捕获 Boss 当前有效模型，必须显式填写，不能隐式推断；
- `slot`：模型包内的投射物槽位，如 `arrow`、`trident` 或未来的 `kunai`、`knife`；
- `model_scale`：仅作用于 YSM/自定义模型的显示尺寸，与 `base_scale` 和实体碰撞尺寸
  分离；
- `max_instances`：该 action 同时允许进入 YSM 路径的数量，超出后按 `fallback` 处理；
- `fallback`：首期固定支持 `yh`，表示回到 YH 原有面片/几何渲染路径；
- `acknowledge_cost`：创建者确认性能成本的显式标记。

模型来源快照、槽位解析和上限判断应发生在客户端生成可见实例时；服务端仍只同步
弹幕定义和权威运动状态，不读取客户端模型文件，也不依赖客户端是否安装 YSM。

## 6. 告警与手动确认

当 action 含有 `ysm_projectile` 时，Spell Analyzer 和 Editor 应显示性能告警，至少
包含模型槽位、预计同时实例数、YSM 路径和 YH 回退路径。未设置
`acknowledge_cost: true` 时，首期可以将符卡标记为“未确认”，并由认证流程决定
是否阻止认证；具体阻断级别在实现前冻结。

运行时告警只用于诊断，不得在渲染循环逐帧刷日志。以下情况采用一次性或汇总提示：

- YSM 未安装或投射物 API 不可用；
- 模型包或槽位不存在；
- action 达到 `max_instances`，部分弹幕回退 YH；
- 解析到不支持的模型来源。

告警不能影响 Boss 当前模型，也不能让一次缺失模型导致整张符卡停止。

## 7. 性能预算与策略

YSM 投射物每颗都可能产生动画/骨骼更新和额外绘制调用；模型复杂度、动画数量、
渲染后端、GPU/CPU 和屏幕内实例数都会改变成本。预开发阶段只把 **8～20 颗同时使用
YSM 的特殊弹幕**作为初始设计范围，不把它写成不可调的硬常量。实际默认值应进入
`YHModConfig` 或 action profile，并通过实机基准修正。

四个 `custom` 变体当前的 YH 回退并不都走同一批处理路径：Cross/Swinging 变体可能
经过实体式 PoseStack 渲染。因此基准必须把“YH 回退”和“YSM 特殊路径”分别测量，不能
简单地把 YSM 成本与普通 Billboard 批处理成本相比较。

建议的运行策略：

1. 普通大量弹幕继续 YH 批处理；未启用 YSM 的 `custom` 弹幕继续现有 YH 几何渲染路径；
2. 特殊 action 先按 `max_instances` 取前 N 个可见实例，其余立即走 YH；
3. 进入/退出 YSM 路径时避免频繁创建和销毁模型对象，复用已探测的模型和槽位缓存；
4. 模型缺失、后端不可用或超限均走同一 YH 回退，不产生额外物理分支；
5. 基准至少覆盖 0、8、20 个特殊投射物，并分别记录 GPU、Compatibility 后端和
   无 YSM 环境的帧时间/批次数。测试结果用于调整建议范围，而不是反向改变符卡逻辑。

作为风格探索层，YSM 允许较高模型复杂度；资源定型后，如果数量需求上升，应评估
将模型烘焙或移植为 YH 批处理模型，而不是无限提高 YSM 实例上限。

## 8. 分阶段计划

### Phase 0：契约与探测

- 确认当前 OYSM/YSM 版本是否提供可调用的虚拟投射物渲染入口；记录反射签名和失败
  降级行为。
- 定义 `custom + variant` 数据结构、旧四项到变体的临时迁移映射、旧引用清理清单、
  action 草案、模型来源快照、槽位目录和 `max_instances` 语义。
- 接通 Analyzer/Editor 告警、确认标记和运行时一次性诊断，但暂不启用真实渲染。

### Phase 1：少量弹幕桥接

- 在 YH 自有兼容层实现虚拟投射物桥，保持服务端权威和 YH 回退。
- 先让 `custom` 的四个变体完整走 YH 回退，再支持已有 YSM `arrow`/`trident` 槽位，
  验证位置、旋转、贴图、尺寸、染色和生命周期。
- 记录无 YSM、槽位缺失、超限三条回退路径。

### Phase 2：编辑器与预览

- Editor 提供模型包、槽位和上限的选择/预览。
- 显示模型来源、当前 action 影响范围和性能告警；支持拆分 action 以混用 YH/YSM。
- 不把客户端资源探测结果写入服务端权威存档。

### Phase 3：专用资源与风格探索

- 为妖梦模型包补充 `kunai`、`knife` 等专用投射物资源，或明确其与现有槽位的复用关系。
- 用少量 `custom` 弹幕验证四个变体的辨识度、贴图一致性、尺寸/染色变化和动作稳定性。
- Shooter 继续单独使用 `main.json` LivingEntity 管线，不与弹幕槽位混用。

### Phase 4：基准与启用范围

- 完成 0/8/20 实例、不同后端、不同模型复杂度的实机基准。
- 根据结果调整配置默认值、Analyzer 警告级别和认证规则。
- 只有在实机截图或 `/yhysm debug` 快照证明画面、回退和生命周期正确后，才扩大默认启用范围。

## 9. 验收条件

- 无 YSM、YSM API 不兼容或模型缺失时，YH 可以正常启动，Boss、Shooter 和普通弹幕
  均保持原行为。
- `base_scale` 与 `model_scale` 分离验证：前者改变模型、判定箱和剔除，后者只改变
  模型显示大小；两者不会互相污染。
- action 明确指定的弹幕才进入 YSM；Boss 切换模型不会改变已生成弹幕；Shooter
  模型与弹幕模型互不覆盖。
- 超过上限的弹幕稳定回到对应 `custom` 变体的 YH 回退路径，且不会产生每帧日志。
- Editor/Analyzer 能显示成本、槽位、上限和回退路径，并能记录创建者确认状态。
- 实机验证 `kunai`、`knife`、`scale`、`talisman` 四个 `custom` 变体的朝向、贴图、
  模型动画、尺寸、染色、出生/销毁时机和飞行轨迹；确认与 YH 共同飞行轨迹时不改变
  碰撞和擦弹判定。
- 提交前通过 `git diff --check`；实现阶段再按 `AGENTS.md` 集中执行必要的
  `compileJava`/`organizeLang`，不以编译通过代替 YSM 画面验收。

## 10. 风险与未决问题

1. **YSM 没有稳定的虚拟投射物入口**：需要评估真实 Projectile 视觉通道，或延后到
   第三方 API 可用后再实施；不能假设 LivingEntity 委托可直接复用。
2. **模型槽位命名和元数据格式**：当前模型包仅确认 `arrow`、`trident`；`kunai`、
   `knife` 的目录和注册名需与实际 YSM 解析规则核对。
3. **玩家 `main.json` 的专属逻辑**：妖梦包的玩家动作、MoLang 变量和姿态可能不适合
   Shooter 或投射物，需要单独的专用资源或适配层。
4. **认证阻断级别**：`acknowledge_cost` 缺失时是阻止认证、仅标红，还是允许带未确认
   标记发布，需要结合 Editor/认证流程最终决定。
5. **模型切换时机**：首期按生成时快照处理；若未来需要动态换肤，必须另行定义缓存、
   网络同步和性能语义，不能偷偷改变当前契约。
6. **批处理与 YSM 混用顺序**：需要实机确认透明度、深度和渲染层顺序，不得破坏现有
   法阵、阴影和实体委托链。

本计划的下一步是先完成 Phase 0 的 API/模型包探测和 Analyzer 告警设计，再决定是否
进入桥接实现；在此之前不冻结 `ysm_projectile` 字段，也不承诺具体第三方版本兼容范围。
