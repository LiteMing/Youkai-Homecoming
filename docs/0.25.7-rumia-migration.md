# 0.25.7 Rumia spell migration

Rumia did not previously have a `SpellDefinition`. The `rumia` and `ex_rumia`
IDs were only used by the spell-circle renderer; all attacks lived in
`RumiaAttackGoal` and `RumiaStateMachine`.

## Split of responsibilities

- `SpellRuntime` owns the primary ranged red/black volley (`rumia` and
  `ex_rumia`). The normal form fires three waves every 40 ticks; Ex fires five
  waves every 20 ticks.
- `RumiaAttackGoal` still handles the nearby secondary targets. This keeps the
  old multi-target behavior without emitting the primary volley twice.
- `RumiaEntity` and `RumiaStateMachine` remain authoritative for Ex conversion,
  attribute modifiers, fire/invulnerability rules, charge movement, blocking,
  melee damage, and knockback. The damage-triggered retaliation volley is now
  part of the `on_damage` list in the migrated definition (12 red projectiles
  for normal Rumia, 24 for Ex, speed 0.8, lifetime 40 ticks, caster origin).

`on_damage` is invoked by the real Boss hurt path and uses the existing target
direction (`AimMode.Target`). The Preview control bar has a transient
on-damage interval (in ticks, zero disables it) that simulates the target
attacking the preview caster; it does not make the target cast a spell.

During Rumia's charge-flight and blocked stages the legacy retaliation volley
remains suppressed. A blocked hit still shortens the block timer as before.

Rumia does not install a `SpellCardWrapper`; `YoukaiAttackGoal` uses that
distinction to preserve the physical charge attack while the runtime schedules
the ranged pattern. Runtime state is persisted using the normal `SpellRuntime`
NBT payload and restored by `RumiaEntity`.
