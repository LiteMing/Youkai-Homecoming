## 1. 背景与目标

现有 `PlaySoundAction` 已接入 Editor 的 `Presentation` 分组,但仍有多项限制:

- 声音固定从施法者位置发出;
- 固定使用 `HOSTILE` 分类;
- 命中时不能自然从 `hitPosition` 发声;
- 没有听众、半径、衰减等统一模型;
- Camera Shake 尚无对应 Action;
- Preview 和实机缺少统一的表现层执行接口。

本项目 (Youkai's Homecoming, Minecraft Forge mod) 拥有一套数据驱动的东方 Project 风格弹幕系统
(符卡 SpellDefinition → SpellRuntime → 弹幕实体),以及一个符卡编辑器/正交预览系统。

目标:建立一层轻量的 **Client Feedback / Presentation Cue** 系统,将世界表现(位置音效/粒子)
与观察者表现(镜头抖动/屏幕闪光)统一封装为 Cue,由服务端授权、衰减、合并后批量下发,
客户端负责实际表现与无障碍限制,Editor 使用本地 sink 预览。

## 2. 设计总览

### 2.1 两类表现效果

**世界表现**(有世界坐标,附近所有玩家都可能观察到):

- 位置音效
- 粒子
- 冲击环
- 短暂光效

服务器决定发生位置,并广播给附近玩家。

**观察者表现**(直接作用于某个玩家的画面或设备):

- 镜头抖动
- 屏幕闪光
- 色差/暗角
- 低血量脉冲
- 手柄震动

它们不是世界实体状态,而是服务器请求客户端播放的提示效果。

Camera Shake 属于第二类,但通常仍有世界空间来源——爆炸点越近,镜头抖动越强。

### 2.2 统一 Feedback Sink

Action 不应直接依赖客户端类,也不要让每个 Action 各自写网络逻辑。

```java
interface SpellFeedbackSink {
    void playSound(SoundCue cue);
    void cameraShake(CameraShakeCue cue);
}
```

不同环境使用不同实现:

```
ServerFeedbackSink → 校验、筛选玩家、发送 cue packet
PreviewFeedbackSink → 为 Editor 预览视口提供本地消费者
NoopFeedbackSink     → 纯服务端分析或不支持表现的环境
```

`SpellContext` 暴露:

```java
ctx.feedback().cameraShake(cue);
```

Action 层也可以按具体效果调用 sink:

```java
ctx.feedback().playSound(cue);
ctx.feedback().cameraShake(cue);
```

这样同一个 Action 在实机服务器、单人游戏、Editor Preview、认证战中使用同一套语义；Preview sink 的声音/视口消费者由编辑器接入层提供。

### 2.3 系统架构

```
Action (SoundCue / CameraShakeCue)
    │
    ▼
SpellFeedbackSink
    │
    ├── ServerFeedbackSink ──► 服务端校验/限流/合并 ──► SpellFeedbackPacket ──► 客户端
    │                                                                    │
    ├── PreviewFeedbackSink ──► 预览视口本地播放                      ▼
    └── NoopFeedbackSink     ──► 静默                           ClientFeedbackManager
                                                                    ├── CameraShakeManager
                                                                    ├── SoundPlayer
                                                                    └── AccessibilityScale
```

## 4. 核心设计约束(违反即返工)

- **CF-1 服务端权威**:所有 cue 的强度、半径、合并由服务端决定并同步;客户端仅负责表现,
  不得推断战斗状态或反向驱动判定。
- **CF-2 镜头抖动不改玩家朝向**:禁止 `setYRot` / `setXRot`——干扰瞄准、产生朝向分叉、
  与其他模组摄像机冲突、抖动结束后难以恢复。shake 是纯视觉 offset,叠加在 camera transform
  上,不写回玩家实体朝向。
- **CF-3 客户端无障碍最终控制**:服务端只能请求 `intensity = 0.5`;客户端按
  `effectiveIntensity = requested × accessibilityScale` 实际生效,不得强制覆盖。
- **CF-4 噪声平滑**:shake 使用带 seed 的平滑噪声(Perlin/Simplex 或平滑正弦混合),
  禁止每帧完全随机——否则画面产生刺眼高频跳变。
- **CF-5 合并优先于叠加**:同 channel、相近位置、同 tick 的大量事件必须合并(如 100 颗弹幕
  撞墙合并为一个受限 Impact Cue),不能简单相加导致高密度弹幕下画面不可用。
- **CF-6 配置是唯一调参真源**:所有可调数值(强度上限、半径上限、每 tick cue 数量上限等)
  进 `YHModConfig`;实体/渲染器不再放第二份默认值。
- **CF-7 无客户端随机**:Pilot/Cue 层零随机(确定性扰动用于打破对称),可复现。

## 5. 分阶段计划

### Phase 0 — Feedback Sink 接口与 Cue 数据模型
**产出**:`content/spell/feedback/` 包

- `SoundCue`:sound, source(SoundSource), origin(caster/target/action/hit), position(可空,
  空则按 origin 解析), volume, pitch, radius(可空), attenuation(boolean)。
- `CameraShakeCue`:origin, intensity(0.0~1.0), duration(1~40 tick, Boss/OP 可放宽到 100),
  frequency, radius, falloff(none/linear/quadratic), channel(impact/warning/ambient)。
- `SpellFeedbackSink` 接口:`playSound(SoundCue)` / `cameraShake(CameraShakeCue)`。
- `ServerFeedbackSink`:校验参数、筛选玩家、将 cue 序列化进 `SpellFeedbackPacket`。
- `PreviewFeedbackSink`:为预览视口提供本地消费者,绕过网络；默认空消费者用于未接入预览表现的分析场景。
- `NoopFeedbackSink`:静默实现,用于纯服务端分析。
- `SpellFeedbackPacket`:批量传输,`List<FeedbackCue>`。
- `SpellContext.feedback()`:暴露当前 sink,Action 通过 `playSound(cue)` / `cameraShake(cue)` 发送。

### Phase 1 — PlaySoundAction 迁移到 SoundCue
**产出**:扩展 `PlaySoundAction`

- 支持新参数:`source`, `origin`, `radius`, `attenuation`。
- `origin` 支持:`caster` / `target` / `action` / `hit`。
- `action` 作为默认值,因为 Trail/Hit callback 的 `TrailCardHolder.center()` 已倾向于代表事件发生位置。
- `source` 默认 `hostile`;`origin` 默认 `caster`——旧 JSON 缺省,保持现有行为。
- `radius` 和 `attenuation` 为可选项,缺省走 vanilla 默认行为。
- `hit` origin 仅在 on-hit 中可用,使用 `SpellHitContext.hitPosition()`。

### Phase 2 — CameraShakeAction + 客户端 CameraShakeManager
**产出**:`CameraShakeAction` + 客户端管理

- `CameraShakeAction` JSON 参数:`origin`, `intensity`, `duration`, `frequency`, `radius`,
  `falloff`, `channel`。
- `origin` 支持:`caster` / `target` / `action` / `hit`。
- `CameraShakeManager`(客户端单例):
  - 维护 per-channel 活跃 shake 状态;
  - 同 channel 合并:位置取最大幅度或有限 RMS,持续时间取较大值,频率按最大强度事件,
    总强度最终 clamp 到 `CLIENT_MAX_SHAKE`;
  - 使用平滑噪声生成每帧 offset(不写回玩家朝向);
  - 在 Camera Setup/Render Camera 阶段添加纯视觉 translation + rotation offset。
- 距离衰减:

```java
double distanceRatio = clamp(distance / radius, 0, 1);
double attenuation = switch (falloff) {
    case NONE -> 1;
    case LINEAR -> 1 - distanceRatio;
    case QUADRATIC -> {
        double x = 1 - distanceRatio;
        yield x * x;
    }
};
effectiveIntensity = configuredIntensity * attenuation * clientAccessibilityScale;
```

- 客户端无障碍设置:通过 `YHModConfig` 提供 `Off / Reduced / Full` + 强度 0~100%。

### Phase 3 — 批量 SpellFeedbackPacket + 服务端限流
**产出**:网络层与限流

- `SpellFeedbackPacket` 批量传输:`List<FeedbackCue>`。
- 服务端按 tick、维度、接收玩家批处理,不要每个 Action 一个 packet。
- 同 sound + 相近位置 + 同 tick 的大量声音合并音量(合并或采样,不重复播放)。
- 服务端限流规则(普通基底, Boss/OP 节点再放宽):
  - Camera intensity ≤ 0.5
  - Duration ≤ 40 tick
  - Radius ≤ 32
  - 每张符卡每 tick cue 数量有上限
  - 每个观察者每 tick 接收数量有上限
- 合并策略:同 channel / 相近位置 / 同 tick → 合并为一个强度受限的 Cue。

### Phase 4 — Editor 接入
**产出**:Editor 分组与 Preview

- 将 `Presentation` 分组扩展或新建 `Client Feedback` 分组:

```
Presentation
├── Play Sound
├── Show Spell Title
├── Custom Magic Circle
└── YSM Render

Client Feedback
├── Camera Shake
└── (预留 Screen Flash / Warning Pulse)
```

- 给纯客户端节点加图标标识(如 🖥 Camera Shake)。
- `CameraShakeAction` 节点选中后显示参数面板:

```
Preset
Origin
Intensity
Duration
Frequency
Radius
Falloff
Channel
```

- **预设**(比全参数更重要):

```

```

  用户选择预设后仍可展开 Advanced 覆盖参数。

- **Editor Preview 处理**:
  - 提供开关:`Client Feedback Preview: On/Off`、`Camera Shake Preview: On/Off`、`Sound Preview: On/Off`。
  - 默认 `Sound = On`;`Camera Shake = On` 但强度上限 30%~50%。
  - 只抖动预览视口,不抖动整个 GUI。
  - 提供 `Test Shake` 按钮。
  - Preview Timeline 中显示事件标签(如 `Tick 40: Camera Shake 0.35 / 12t`)。

### Phase 5 — Analyzer cue 次数上界 + 复杂度映射
**产出**:分析与成本

- 新增内部统计:`maxClientCuesPerTick`、`totalClientCues`。
- 高危来源放大:

```
Camera Shake in on_hit_block × (max_bounces + 1)
Sound in on_trail × hook_count
```

- 映射到现有综合复杂度成本,不一定要暴露成新的玩家技术字段。
- 如果无法证明 cue 上界,认证 fail-closed。
- 运行时仍必须限流,因为静态分析不能保证多个玩家符卡同时运行时的总量。

| 风险 | 缓解 |
|---|---|
| 镜头抖动直接写玩家朝向,干扰瞄准 | CF-2 硬约束;shake 是纯视觉 offset,不动实体朝向 |
| 高密度弹幕下 cue 包爆炸 → 卡顿/崩画面 | CF-5 合并策略 + 服务端限流 + 批量 packet |

| 无障碍降级被忽视,shake 成为唯一预警 | CF-3 + 验收项明确检查关闭 shake 后的替代提示 |

| 噪声随机导致每帧跳变,画面刺眼 | CF-4 硬约束;使用平滑噪声,禁止纯随机 |

## 9. 后续方向：Freeze Projectiles（待远端审查确认可行性）

> 以下内容为调研草案，**不纳入 0.26.0 最小落地范围**，待远端审查后确定可行性并独立立项。

### 9.1 为什么需要独立节点

`HoldSourceAction` 已实现**单弹幕命中后冻结**（固定位置 + `HitHoldMover` + 到期恢复），但它不应被 `DelayAction` 或通用延迟节点承载。命中后冻结源弹幕、决定后续碰撞结果，属于**命中控制（Hit Control）**，不是时间调度。

建议拆成三个独立概念：

| 节点 | 职责 | 当前状态 |
|---|---|---|
| `delay` | 纯时间调度，推迟 Action 执行，不冻结任何实体 | 已有 `DelayAction`，应恢复其原始语义 |
| `hold_source` | 命中后暂停**当前源弹幕**，到期后执行 `on_release`（bounce/continue/discard） | 已有 `HoldSourceAction` |
| `freeze_projectiles` | **范围链式冻结**：从触发点向周围传播冻结，影响多颗弹幕，到期后恢复原轨迹 | **待实现** |

### 9.2 核心接口设计（草案）

```java
// 弹幕冻结状态
public enum FrozenState {
    UNFROZEN,
    HIT_HOLD,        // 命中暂停：决定新轨迹（bounce/continue/discard）
    GAMEPLAY_FREEZE  // 游戏冻结：恢复旧轨迹，暂停 mover 局部时间
}

// 冻结配置
public record FreezeProjectilesConfig(
    Vec3 origin,
    double radius,
    int duration,
    int maxTargets,
    int maxGeneration,
    int propagationDelay
) {}
```

### 9.3 与现有系统的整合点

#### 9.3.1 现有基础设施可复用

- `SpellHitContext` 已有 `HitDisposition.HOLD` + `holdTicks` + `deferredBody` + `beginResumeAndTakeBody()`
- `HitHoldMover` 已有零速度 mover
- `SpellRuntime.scheduleDelayed` 已有延迟调度
- `UserMatrixCache` / `EntityStorageCache` / `SectionCache` 已有空间查询能力
- `ParallelTicker` 已有批量弹幕 tick 流程

#### 9.3.2 必须新增的内容

1. **弹幕冻结状态字段**：`ItemDanmakuEntity` 增加 `freezeTicks` + `FrozenState`，tick 时递减
2. **范围弹幕查询**：基于 `EntityStorageCache` 或新增空间索引，支持"某位置周围 N 格内的所有弹幕"
3. **有界 BFS 传播**：`max_targets`（全局累计）+ `max_generation` + `propagation_delay` + visited 集合去重
4. **恢复策略区分**：
   - `HIT_HOLD`：从碰撞点决定新轨迹（现有逻辑）
   - `GAMEPLAY_FREEZE`：恢复原 mover + 调整局部时间 `effectiveMoverTick = tickCount - accumulatedPausedTicks`
5. **客户端同步**：冻结开始/恢复的 packet（批量，类似 `BatchEraseDanmakuToClient`）

#### 9.3.3 冻结期间的 tick 行为

`ParallelTicker` 流程中，冻结弹幕应：
- **跳过** `planMove/trimMove/applyMoveTick`（不移动）
- **保留** `collectCollisionInput` + `resolveCollision`（仍检测实体命中，`hit_entity = discard` 检测成本仍在但处理便宜）
- **保留** `finishTick`（trail action、graze 等）

### 9.4 性能边界建议

| 参数 | 建议上限 | 说明 |
|---|---|---|
| `radius` | 8 格 | 超过 8 格候选弹幕爆炸式增长 |
| `max_targets` | 64 | 单次冻结全局累计上限 |
| `max_generation` | 4 | 传播深度，防止链式 BFS 失控 |
| `propagation_delay` | 2 tick | 每代传播间隔 |
| 单 tick 传播代数 | 1 | 每 tick 只推进一代，避免帧峰值 |

**硬规则**：
- 如果无法证明候选弹幕上界，认证 fail-closed
- 运行时仍必须限流，因为静态分析不能保证多个玩家符卡同时运行时的总量
- `max_targets` 是**全局累计**，不是每代独立

### 9.5 目标筛选的当前限制

当前无弹幕标签/组系统。第一版只能按以下条件筛选：
- **半径**：`radius` 参数
- **Owner 敌对关系**：`canHitDanmakuTarget` / `shouldHurt`
- **BulletCategory**：`NORMAL` / `GIANT`（`YHDanmaku.Bullet.category`）
- **实体类型**：`ItemDanmakuEntity` / `YHBaseLaserEntity`

未来若需更精细筛选（如"只冻结红色弹幕"），需在 `ItemDanmakuEntity` 上增加 `Set<ResourceLocation> tags` 或 `int freezeFlags`。

### 9.6 与 HoldSource 的关系

现有 `HoldSourceAction` 的 HOLD 逻辑可直接作为 `HIT_HOLD` 子类型复用。两者共用：

```
SpellHitContext.HitDisposition.HOLD
hitCtx.holdTicks
hitCtx.deferredBody
hitCtx.beginResumeAndTakeBody()
```

但 `freeze_projectiles` 不应走 `SpellHitContext`，因为它是范围效果，不是单弹幕命中结果。它应是独立的 Action，直接操作弹幕实体状态。

### 9.7 实施顺序建议

1. **Phase 1：基础冻结状态** — `ItemDanmakuEntity` 加 `freezeTicks` + `FrozenState` 枚举，tick 时跳过移动
2. **Phase 2：FreezeProjectiles Action** — 实现 `freeze_projectiles` action，参数：`origin/radius/duration/max_targets/max_generation/propagation_delay`
3. **Phase 3：空间查询优化** — 实现范围弹幕查询（基于 `EntityStorageCache` 或新增空间索引）
4. **Phase 4：传播与恢复** — 有界 BFS + visited 去重 + 到期恢复原轨迹
5. **Phase 5：客户端表现** — 冻结视觉特效 + 同步 packet

### 9.8 风险清单

| 风险 | 缓解 |
|---|---|
| 每颗弹幕创建 FreezeMover 对象开销 | 第一版用 `freezeTicks` 字段，不替换 mover |
| 空间查询 O(N²) | 必须用空间索引 + visited 集合 + max_targets 硬限制 |
| 冻结期间实体碰撞检测仍昂贵 | 保留检测但简化处理；discard 后弹幕删除反而减少后续成本 |
| 恢复后 mover 时间不同步 | GAMEPLAY_FREEZE 需调整 `effectiveMoverTick = tickCount - accumulatedPausedTicks` |
| 无标签系统导致筛选粗糙 | 第一版按 owner + BulletCategory 筛选，后续扩展 tag |
| 多代传播在单 tick 内爆发 | 每 tick 只推进一代，propagation_delay 控制节奏 |
| 与 HoldSource 语义混淆 | Editor 分组明确分离：命中控制 vs 弹幕控制 |

### 9.9 Editor 结构建议

```
命中控制
├── 反弹
├── 穿透
├── 结束弹幕寿命
├── 抹除弹幕
└── 命中后冻结
    ├── 冻结时长
    └── 释放时动作

弹幕控制（未来独立分组）
├── 冻结范围内弹幕
├── 解冻弹幕
├── 碎裂冻结弹幕
└── 清除弹幕
```

不要把未来链式冻结全部塞到 `hold_source` 里。`hold_source` 只处理**当前源弹幕**的命中暂停，`freeze_projectiles` 处理**范围弹幕**的游戏性冻结。
