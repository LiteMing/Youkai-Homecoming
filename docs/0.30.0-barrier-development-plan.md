# 0.30.0 开发计划：结界（Barrier）

> 状态：预开发设计，尚未进入实现。
>
> 本文只定义 0.30.0 的数据模型、运行时边界、渲染策略和编辑器入口。Koishi、Doremy
> 的现有符卡行为继续作为基线；计划优先增加可见性和可配置性，再逐步接入弹幕修改与
> 脚本事件。

## 1. 目标与范围

0.30.0 的结界系统需要同时覆盖四类需求：

1. Koishi：以施法者为中心的球形体积结界，表现现有 32 格限制和界外弹生成。
2. Doremy：两个平行面组成的薄层结界，兜住 Maze 模式的上下激光层。
3. 结界表现：形状、材质、颜色、边缘、内部屏幕滤镜和动画参数可由数据定义。
4. 符卡编辑器：可以选择已注册结界，并快速调整实例的大小、持续时间和移动方式。

首期不改变 Koishi 的推回算法、Doremy 的 Ground/Maze 状态机，也不把每个结界做成
Minecraft 实体。服务端继续持有结界状态，客户端只接收快照并负责渲染投影。

## 2. 已有行为基线

Koishi 的运行时已经是球形距离约束：距离超过 26 格后可能在目标未来方向生成边界弹，
超过 32 格后把目标移回球面并施加向内速度。实现位于
`content/spell/game/KoishiSpell.java`，数据驱动路径使用
`content/spell/action/ConfineTargetAction.java`。

Doremy 没有空间边界。它累计目标着地时间，连续 20 tick 后触发 Maze；目标离地后转向
Madness。Maze 的激光发射点位于目标附近的两个高度层，因此结界视觉应表现为上下两张
平行面，而不是包围整个目标的透明盒子。

## 3. 统一模型

### 3.1 注册定义与实例

结界分为两个层次：

- `BarrierDefinition`：数据包或内置资源注册的只读定义，包含形状、材质、滤镜和默认行为。
- `BarrierInstance`：服务端运行时实例，包含中心、朝向、缩放、剩余时间、移动状态、所有者、
  优先级和当前激活状态。

符卡 action 只保存注册 ID 和实例覆盖参数，不复制整份材质定义。这样可以在编辑器中快速
切换预设，也能保证服务端对未知 ID 拒绝或回退。

### 3.2 形状接口

形状接口必须同时提供粗筛和精确判定：

```text
bounds(instance)       // AABB，用于区块索引和视锥剔除
contains(instance,pos) // 精确的点是否在体积内
intersect(instance,a,b)// 线段穿越结界的交点
```

首期形状：

- `sphere_volume`：Koishi 使用，半径默认 32；
- `parallel_planes`：Doremy 使用，两张有朝向的平面，带间距、宽度和长度；
- `box_volume`：编辑器和脚本的通用染色盒子；
- `polygon_surface`：圆、多边形、五角星等表面图形，只负责视觉或边界线，可选是否附带体积。

AABB 只作空间索引，不能代替球体或多边形的真实判定。表面图形和体积判定必须允许独立配置。

### 3.3 表现定义

建议的资源结构如下：

```json
{
  "shape": {
    "type": "sphere_volume",
    "radius": 32
  },
  "appearance": {
    "edge": "outline",
    "material": "youkaishomecoming:barrier/koishi",
    "color": "#55AAFF",
    "alpha": 0.18,
    "edge_alpha": 0.9,
    "pulse_period": 40,
    "world_layer": "additive"
  },
  "inside_effect": {
    "texture": "youkaishomecoming:textures/barrier/koishi_filter.png",
    "color": "#3366AA",
    "alpha": 0.16,
    "blend": "alpha",
    "priority": 10
  },
  "defaults": {
    "duration": 200,
    "scale": 1.0
  }
}
```

`material` 只描述客户端资源。服务端不依赖材质存在与否；材质缺失时客户端使用线框和纯色回退。
所有可调数值应最终接入 `YHModConfig` 的上限或性能预算，避免实体、渲染器和配置各自保存默认值。

## 4. 两个首期预设

### 4.1 Koishi 球形体积结界

- 中心：施法者 `holder.center()` 的服务端快照；
- 半径：默认 32，边界预警半径 26 作为可选内圈提示；
- 世界表现：低 alpha 球面只作为辅助，主要显示经纬线/脉冲轮廓和目标移动方向上的边界弹；
- 内部表现：摄像机进入球体后启用屏幕染色和轻微纹理滤镜；
- 物理：继续使用现有 `ConfineTargetAction`，首期不替换为通用 Barrier 碰撞代码。

这样可以先验证“现有 Koishi 行为 + 结界视觉”是否足够还原，再决定是否把推回逻辑迁移到
通用 `contains/intersect` 接口。

### 4.2 Doremy 双平行面结界

- 中心：Maze 触发时锁定目标位置；
- 几何：两张水平或按目标朝向旋转的平面，间距覆盖两层激光的高度；
- 表现：两面使用同一材质但相反方向流动，边缘用高亮线；
- 生命周期：与 Maze ticker 对齐，结束时淡出；
- 物理：首期只用于表现和调试，不拦截玩家或弹幕。

双平面定义应允许独立设置中心偏移、法线、间距、面尺寸和移动方式，以便以后表达竖直墙面或
倾斜结界。

## 5. 渲染与透明度策略

Minecraft 不提供跨实体、跨 RenderType 的全局透明排序。结界不能依赖透明实心盒子来保证多个
结界的正确叠加。

渲染分为两层：

1. **世界层**：边缘、线框、符号、脉冲和少量不透明/加法混合面。按材质批处理、视锥剔除，
   不创建实体；必要时使用深度测试保证结界不会覆盖近处实体。
2. **屏幕层**：摄像机处于结界内部时，复用 `GiantDanmakuScreenOverlay` 的全屏四边形路径，
   进行染色、纹理和暗角混合。为控制成本，最多保留 2～4 个按 `priority` 和实例 ID 排序的滤镜层。

世界层必须始终保留可识别的边缘，即使屏幕滤镜被关闭、材质缺失或 shader 兼容层不可用。首期不
引入 stencil 或自定义全屏深度纹理，以降低 Oculus/软依赖组合的风险。

客户端集中管理：

```text
BarrierRenderManager
  -> 可见实例收集与 AABB/视锥剔除
  -> 按材质分组的缓存网格
  -> 世界层批处理
  -> 摄像机 contains() 查询
  -> 屏幕滤镜层选择与混合
```

## 6. 符卡编辑器入口

### 6.1 独立 Barrier Editor

结界需要独立的编辑器面板或编辑器类型，原因是它同时包含几何、材质和屏幕滤镜，字段数量和
生命周期语义都明显不同于普通 `fire_danmaku`。

独立编辑器负责：

- 创建和校验 `BarrierDefinition`；
- 预览 sphere、parallel planes、box、polygon_surface；
- 调整颜色、alpha、材质、脉冲、滤镜和优先级；
- 显示性能估算（世界绘制批次、滤镜层数、网格顶点数）；
- 导出注册资源或嵌入符卡草稿。

首期不允许编辑器直接注册服务器全局定义。编辑器导出后仍需经过现有 Codec、Analyzer 和认证流程。

### 6.2 现有符卡编辑器中的快速调用

在 action 编辑器中增加 `barrier` 节点，字段保持短小：

```json
{
  "type": "barrier",
  "barrier": "youkaishomecoming:koishi_sphere",
  "scale": 1.0,
  "duration": 200,
  "motion": {
    "type": "follow_target",
    "offset": [0, 0, 0]
  }
}
```

编辑器交互顺序：

1. 下拉选择已注册结界；
2. 显示该结界支持的覆盖字段；
3. 快捷修改大小、时长和移动方式；
4. 高级按钮打开 Barrier Editor，编辑材质或滤镜；
5. 预览窗口同时显示结界、弹幕和摄像机内部效果。

`scale` 只覆盖实例尺寸，`duration` 只覆盖生命周期，`motion` 只覆盖中心/朝向轨迹。它们不能
修改注册定义中的物理语义或越过服务端上限。

### 6.3 与现有符卡兼容

- 旧符卡没有 `barrier` action 时行为完全不变；
- Koishi/Doremy 内置符卡首期可以在运行时旁路生成视觉实例，不立即改写原有 action；
- 未知结界 ID、材质缺失或客户端不支持时，服务端符卡继续运行，客户端显示线框回退；
- Barrier action 是否允许 `on_enter/on_exit`、弹幕修改等实验能力，必须单独计入认证预算。

## 7. 事件与弹幕修改路线

### 7.1 进出事件

服务端每 tick 对玩家和目标实体保存上一个 `contains` 状态，只在状态变化时产生：

```text
barrier_enter(entity, barrier_id, instance_id)
barrier_exit(entity, barrier_id, instance_id)
```

事件应先作为内部运行时 hook 验证，不立即冻结为跨模组公开 API。确认参数和生命周期后再登记
KubeJS/YHStgApi 契约。

### 7.2 弹幕修改

弹幕修改应在移动计划阶段应用，而不是在进入时永久乘改实体速度：

```text
base movement + active barrier modifiers -> final movement
```

首期只保存 modifier 快照和调试信息，待 Koishi 球体、Doremy 双平面的实机表现稳定后，再接入
速度、视觉尺寸和颜色修改。视觉尺寸必须与碰撞尺寸分离。

## 8. 性能与稳定性预算

- 服务端不为结界创建实体；
- 结界查询使用区块/网格索引，不遍历全世界实例；
- 客户端世界层按材质批处理，视锥外实例不绘制；
- 屏幕滤镜最多 4 层，默认 1 层；
- 每个实例的网格缓存只在尺寸、朝向或材质改变时重建；
- 玩家 ENTER/EXIT 不重复发送；
- 无 OYSM、无 Oculus、无 TLM 时结界仍能显示基础线框并保持符卡行为；
- 渲染循环禁止调试日志，调试快照通过显式命令或开发配置开启。

## 9. 分阶段实施

### Phase 0：协议和资源样例

- 确定 `BarrierDefinition`/`BarrierInstance` Codec；
- 加入 Koishi sphere 和 Doremy parallel planes 两个内置资源；
- 建立客户端快照同步和未知资源回退；
- 不接入弹幕修改和公开事件。

### Phase 1：世界层视觉

- 实现集中式 `BarrierRenderManager`；
- 完成 sphere、parallel planes、box、polygon_surface 的边缘渲染；
- 完成视锥剔除、材质批处理和基础性能计数；
- 在 Koishi/Doremy 实际符卡中生成视觉实例。

### Phase 2：Moon 风格屏幕滤镜

- 把现有单层 overlay 扩展为有限滤镜层；
- 按 priority/instance ID 稳定排序；
- 摄像机进入/离开结界时平滑淡入淡出；
- 验证多个结界叠加时的识别度和额外 pass 成本。

### Phase 3：Barrier Editor 与符卡 action

- 新增独立 Barrier Editor；
- 现有符卡编辑器增加注册结界下拉和大小/时长/移动快捷字段；
- 预览窗口支持摄像机进入结界；
- 通过 Codec、Analyzer、认证和服务器同步链路。

### Phase 4：事件和弹幕 modifier

- 内部 `barrier_enter/exit` hook；
- 玩家和目标实体状态变化测试；
- 移动阶段接入速度、视觉尺寸、颜色 modifier；
- 评估是否冻结为 KubeJS/YHStgApi 公开契约。

## 10. 验收标准

### 必须通过

- Koishi 球形结界的边界与现有 32 格推回位置一致；
- Doremy 双平面覆盖 Maze 两层激光，生命周期与 Maze ticker 一致；
- 结界材质缺失、无 OYSM/Oculus/TLM 时仍能启动并显示线框回退；
- 两个以上结界同时存在时不会出现透明实心盒子遮挡或随机层序；
- 旧符卡加载、编辑、认证和运行结果不变；
- 编辑器可从已注册 ID 创建实例，并调整大小、时长和移动；
- 所有新增数值均有明确上限和性能预算。

### 发布前实机验证

- Koishi：目标接近、进入、越过球面时的边缘提示、推回和屏幕滤镜；
- Doremy：Maze 生成、双面淡入淡出、玩家在两面之间移动；
- 多结界：嵌套、相交、不同优先级和不同材质；
- 高弹幕数量下的帧时间、批次数和滤镜 pass 数；
- shader 组合和软依赖缺失场景。

## 11. 尚待确认的决策

1. TH19“附灵结界”中 C 键动作的准确触发语义和持续时间，需要以实机录屏或可靠资料确认，
   不能仅凭现有 Koishi/Doremy 行为推断。
2. `parallel_planes` 的平面朝向是否固定水平，还是跟随施法者/目标朝向，需要在 Doremy
   实机画面中确认。
3. Barrier action 是否首期开放给普通符卡作者，还是先只作为内置符卡的表现节点。
4. 滤镜最多 2 层还是 4 层，应以目标机器上的帧时间测量决定，默认值暂定 1 层。
