# 符卡复刻玩法方案

## 目标

新增“符卡复刻底片”作为妖归自己的物品。底片不是 Exposure 的胶卷；Exposure 只提供正式拍照事件，TLM 只提供可选的拍摄入口。拍照时由服务端识别实际被拍到并消除的敌对弹幕，累计对应符卡的复刻进度。

完整闭环为：

```text
符卡复刻底片
  -> Exposure/TLM 拍照
  -> 绑定来源符卡并累计进度
  -> 进度达到 100%
  -> 生成玩家自己的 Tier 1 未认证符卡草稿
  -> 编辑、修缮和认证
  -> 成为正式符卡
```

### TLM 1.5.3 入口说明

当前依赖的 TLM 1.5.3 没有通用拍照事件或外部功能注册表。其 `ItemCamera.use` 只在 8 格内
射线命中玩家自己的女仆时执行，并直接把女仆转换成照片物品。兼容层因此监听主手相机右键：
如果射线已命中女仆则完全让 TLM 原逻辑处理；否则仅在视野内确实存在可消除弹幕且玩家至少有
1B 时接管本次使用。接管路径与 Exposure 共用同一个服务端候选扫描、1B 扣除、消弹和复刻事务，
不修改 TLM 源码，也不向通用弹幕实体增加来源字段。未来 TLM 若提供正式事件，应把这个入口替换
为事件适配，但保留共用事务服务。

复刻只复制符卡定义内容，不复制原卡证书、认证完成标记、成本、作者权限、OP 配额或原始 `spell_id`。

## 卡面材质与持久化

拍照产生的 PNG 只作为卡面内容；Tier 外框是独立的客户端 overlay，渲染时按物品当前
`SpellCardRank` 重新生成。因此拍照不会把 Tier 12 等高阶卡覆盖成默认灰框，旧版本已经
带灰框的快照也会被当前等级外框覆盖。

客户端缓存和世界存储都使用同一套 `sha256(rawKey)` 文件键。认证报价返回的完整
`definitionHash` 是服务端权威键，客户端收到服务端快照后写入本地缓存；客户端旧版按裸
canonical hash 写入的文件会在首次读取时迁移到新键。未认证草稿仍按 `spell_id` 缓存，
认证成品按完整 definition bundle hash 请求和恢复，避免重启、重连或依赖阶段变化后卡面丢失。

## 来源识别边界

大多数数据驱动符卡由代理实体驱动：

```text
DanmakuProxyEntity / EntitySpellProxyEntity / YoukaiEntity
  -> SpellRuntime
  -> VirtualDanmakuHolder
  -> 虚拟弹幕
```

代理宿主已经持有权威的 `SpellRuntime` 和 `SpellDefinition.id`。拍照兼容层应从宿主取得来源，再给本次拍照的临时候选弹幕附加来源上下文。不要给每颗弹幕加入通用 `SpellSourceRef`，也不要从弹幕的 projectile owner 反向猜测符卡；真实玩家弹幕的 owner 可能只是普通 `Player`。

拍照上下文使用兼容层窄对象，建议包含：

- `spellId`：来源符卡 ID；
- `hostId`：代理或妖怪宿主的临时实体 UUID，仅用于本次拍照过滤；
- `casterId`：施法者 UUID，仅用于排除自己的弹幕和判断敌对关系；
- `definitionHash`：可选的定义版本标识，用于防止服务器重载后同 ID 定义发生变化。

这些对象只存在于服务端本次拍照生命周期，不写入弹幕 Spawn NBT，也不进入弹幕网络协议。

普通 `PlayerHolder` 直接生成的 loose projectile 没有可靠的符卡来源。第一版可以正常消弹但不计入复刻进度，避免为了兼容旧路径而改变整体弹幕结构。无法 JSON 编解码的 Legacy Java 符卡同样不能承诺完整复制。

## 拍照事务

`ModifyFrameDataEvent` 负责建立一批候选并把统计写入照片；`FrameAddedEvent` 负责消除同一批候选。两个事件必须共享候选集合，不能重新扫描后再猜测数量。

待处理拍照上下文不能使用单个全局静态字段。至少按拍照玩家 UUID 隔离，并在 `FrameAddedEvent`、玩家断线和异常路径清理，避免多玩家同 tick 拍照串结果。

拍照筛选规则：

- 只统计对拍摄者实际有效的敌对弹幕；
- 排除拍摄者自己的弹幕、预览弹幕和无关环境弹幕；
- 同一 projectile 在一次拍照中最多统计一次；
- 每次拍照保留总消除上限，避免性能尖峰；
- 消弹和复刻进度统计共享同一批候选。

一张底片只能绑定一个来源。未绑定底片选择本次有效弹幕数量最多的 `spellId + definitionHash`；平票时只消弹、不增加进度。已经绑定的底片只统计匹配来源，其他来源仍可被正常消除但不增加进度。

## 底片状态机

底片状态至少包含：未绑定、进行中、完成。未完成底片潜行右键时清空来源和进度，恢复为空底片；完成后不再走清空路径，而是由服务端创建草稿并替换物品。

达到 100% 时服务端必须原子地完成以下操作：

1. 根据来源保存的定义快照或可信注册表定义，生成独立的可编辑副本；
2. 生成新的玩家自制符卡 ID；
3. 重写根 ID、`entry_phase` 和所有 phase ID，避免引用原卡身份；
4. 保留所有可 Codec 编解码的节点，包括当前草稿等阶无权认证的实验性或 OP-only 节点；
5. 将副本保存到服务端自制符卡存储和运行时注册表；
6. 把底片替换为未认证的 `DynamicSpellItem` 草稿；
7. 草稿默认保持 Tier 1，且不能直接施放，必须重新认证。

复制必须通过 `SpellDefinition.CODEC` 或等价的深复制路径，不能共享原定义中的可变 phase/action 对象。`item_form`、证书、成本和完成状态使用草稿默认值；弹幕动作、hook、变量和生命计划等符卡内容可以复制。

内部 ID 与显示名称分离。当前玩家命名空间可以沿用 `DynamicSpellItem.playerSpellNamespace`，内部 ID 建议使用：

```text
<player-namespace>:replica_<source-path>_<short-hash>
```

显示名称默认使用来源符卡名称加“复刻”标记，玩家可以在编辑器中修改显示名称。不要把可编辑显示名称直接当作唯一 ID；如将来需要修改内部 ID，应实现“另存为新符卡”并原子更新绑定，而不是原地覆盖。

如果来源定义在达到 100% 时已经不可用，不能静默生成空草稿。应保留完成底片并提示来源快照缺失，或在拍照绑定阶段就拒绝不可恢复的来源。

## 基底等级与实验能力

符卡基底等级控制免费节点、单 tick 生成、峰值存活、总弹幕刻、hook 预算和实验能力授权。复刻底片默认生成 Tier 1，不因为拍到了高阶符卡就直接获得高阶性能预算。

当前实验能力的默认分类由服务器策略决定，而不是复刻物品自行绕过认证。`0.25.4` 的默认策略为：

```text
clear_screen          ALLOW
confine_target        EXPERIMENTAL
erase_enemy_danmaku  OP_ONLY
```

`clear_screen` 只清除施法者自己的弹幕，不应占用实验能力额度。`erase_enemy_danmaku` 可以让玩家制造近似安全区，默认不得通过生存认证；`confine_target` 在认证对等条件下风险较低，可以进入实验授权。

能力策略和每个基底等级的预算/授权由 KJS 在服务器启动脚本中配置，认证分析器、编辑器、报价、草稿保存和最终证书校验必须读取同一份运行时策略。未知能力和不可解码节点继续 fail-closed。

复刻不会额外授予来源符卡使用过的实验能力数量，也不会继承证书或自动提高基底等级。原卡中的
实验性和 OP-only 节点仍保留在复刻草稿中供玩家查看和修缮，但拍照不会解锁它们；最终由当前
Tier、KJS 能力策略和认证分析器 fail-closed 拒绝越权内容。

## 安全和验收

- 来源 ID、定义版本和拍照进度由服务端写入，客户端不能决定绑定对象；
- 复刻定义不得覆盖原符卡或其他玩家的自制符卡；
- 认证开始、报价确认、证书签发和正式施放都要重新检查当前能力策略与草稿预算；
- 需要覆盖代理弹幕、普通 Player owner、Youkai 宿主、混合来源拍照、底片重置、完成转换、定义重载和不可序列化来源；
- 真实服务器应记录来源缺失、候选数量、绑定来源、进度增量和转换失败原因。
