# Authoring a YH spell

Create a recognizable, playable danmaku pattern that follows the player's requested
theme and changes. Use the supplied runtime capability report and checker feedback
for the running game's supported JSON; the field reference explains how to compose it.

## Output and revision contract

For the in-game AI request, return exactly one complete SpellDefinition JSON object.
Do not wrap it in Markdown, explanations, patches, diff markers, or an approval form.
For create, use a fresh `youkaishomecoming:ai_<theme>_<unique_suffix>` ID, never an
example ID. For modify, keep the submitted top-level ID and unrelated fields,
including optional editor metadata. Return the entire revised definition each time.
Use the player's language for new display text; preserve existing translations when
editing. Do not invent installed item icons, translation keys, or YSM model names.

The host checks each response using the same JSON parser, Codec field diagnostics,
and node recovery as the editor. If it supplies a failed draft and `checker_feedback`:

1. Read the field paths and errors against that draft and the original request.
2. Fix the indicated structures while retaining the intended motif, playable timing,
   ID, and unrelated working nodes. A repaired required field is better than deleting
   the whole emitter. Unknown types need a supported equivalent, not a guessed spelling.
3. Return the complete corrected JSON. Do not return the diagnostic or claim a check
   passed before the host has checked it. `broken` nodes are recovery placeholders;
   repair their saved raw content instead of emitting them as the final design.

The host bounds automatic revisions and stops when its checker is satisfied. If the
limit or a provider failure stops repair, it preserves the draft and its diagnostics
for the player. There is no Python schema checker in this workflow. For file authoring
without a running checker, save a complete draft and say it has not been checked in-game.

Generation and repair do not register, certify, equip, or cast anything. Experimental
and operator capability labels describe the later game policy; they are not a reason
to reject a creative draft or request extra approval. Do not promise certification.
Use the registered action/condition names in the runtime report. Avoid unrelated
commands or external resources that the requested design does not need.

## Spell and card structure

Keep `entry_phase`, phase map keys, each phase `id`, and every phase reference consistent.
Write the selected type into `item_form.card_type`: `normal`, `timeout_spell`,
`last_spell`, or `non_spell`; `ex_spell` is a separate boolean trait.

For a new normal, timeout, or last spell card, include `item_form.generate: true` and
a finite `duration`/`hp` plan suited to the request. These item fields are plain integers.
Initialize each declared segment with `spellcard_init` in `on_enter`; its `health`
and `duration` are NumberProviders. An item declaration alone does not initialize the
running segment. Do not repeat initialization in `on_tick`. `set_spell_health` is a
read-compatible alias; export `spellcard_init`. Completion targets `on_timeout` and
`on_break` are single `force_phase` or `force_spell` objects, not arrays.

For a non-spell, build a modest finite ordinary-bullet pattern with explicit
`hit_behavior_entity: "discard"` and `hit_behavior_block: "discard"`. Omit health
initialization, declaration presentation, lasers, and projectile hooks. Prefer simple
bounded movers; changing a complex spell's type label does not make its content a
usable non-spell. These are authoring guidelines; the actual use policy stays in-game.

The minimal example is a complete single-segment card. Other examples isolate
techniques: preserve or add the requested card setup when adapting them. Do not stack
every example or copy its ID, density, palette, or translation keys by default.


## Pattern Design Workflow

Before writing JSON for a new visual spell, define a compact art direction:

- Pick 2-3 repeatable motifs, such as a sphere shell, tilted ring, folding cone, delayed crossfire, orbiting seal, or curved spark stream.
- Pick 1 primary bullet and at most 1-2 accent bullets. Do not use many bullet types to create richness; repeat a good shape with controlled variations instead.
- Pick 3-5 colors that support the spell identity. Avoid full rainbow cycling unless the user asks for chaotic festival-style danmaku.
- Use 2-4 action families in the main loop. More families usually read as noise unless they are spaced by clear intervals or phases.
- Let each motif recur with variations in `count`, `interval`, `angle_offset`, `elevation`, `origin`, `group_rotation`, speed, or mover parameters.

Apply these quality rules:

- Prefer "recognizable pattern plus variation" over one-off effects.
- Preserve negative space. If several actions fire on nearby intervals, lower `count`, increase `interval`, or stagger offsets.
- Use accent bullets sparingly for structure, not decoration. For example, accent stars can mark four gates while balls carry the main seal.
- Do not compensate for a weak trajectory by adding more bullet types, colors, trails, or lasers.
- If a first draft feels busy, reduce bullet/color variety before reducing all motion. If it feels plain, add a new recurring motif or trajectory, not random extra bullets.

## 3D Danmaku Guidance

Do not let a requested 3D pattern become a flat 2D ring with cosmetic rotation:

- Use `sphere`, `sphere_random`, `cone`, or `nested_ring` with meaningful `elevation`, `tilt_angle`, and `group_rotation`.
- Use different `origin.offset_y`, `origin.offset_x`, and `origin.offset_z` values to create high, low, near, and far emitters.
- For repeated side emitters, use `repeat` with `sin_deg($i * angle)` / `cos_deg($i * angle)` offsets around the caster or target when `angle` is in degrees.
- Vary vertical motion or height between motifs. A good 3D spell should still show depth when viewed from an oblique camera.
- Keep the main visual readable from the player's view; avoid filling every depth layer at once.

## Mover Usage

Select movers from the source spell's actual trajectory. They are not limited to
`FormulaMover`, and migration quality drops when every bullet is reduced to a
constant speed line.

- Use `polar`/`orbital` for rotating or radial rings, `bezier`/`multi_bezier`/
  `spline` for authored curves, `composite` for time segments, `layered` for
  additive roles, `translate` for world-space offsets or creation-time aim,
  `homing` for live-target steering, and `formula` for measured per-tick curves.
- FormulaExpr trajectory strings (`formula`, `orbital`, `translate`) are
  evaluated every projectile flight tick. NumberProvider mover parameters are
  normally resolved when the mover is created; do not describe them as live
  unless the runtime code says so.
- When a mover is present, `fire_danmaku.speed` supplies initial velocity or the
  mover's base direction and may be only a required compatibility input. Put the
  visible motion budget in the mover (`translate.speed`, curve duration,
  acceleration, angular speed, or formulas) and keep the visible motion consistent with the requested tuning.
- Combine mover-driven and speed-only bullets when the source pattern does. Do
  not add a mover merely for decoration, but do not omit one when it carries the
  recognizable motion.
- `acceleration` supports optional terminal velocities (`terminal_vx/vy/vz`)
  and `space: "local"` (forward/right/up axes) in addition to the default
  world axes. It is the current mover that can be rebased after a block bounce;
  other movers fall back to the resolved outgoing velocity after a bounce.
- `homing` is live-target steering: `speed` is blocks/tick, `turn_rate` is
  degrees/tick, and `delay` postpones steering. It differs from `translate`'s
  creation-time aim snapshot.
- Angular values in `rotate`, `polar`, and `orbital` (`degrees_per_tick`,
  `initial_angle`, `angular_speed`, and `angular_accel`) are degrees (the
  speed/acceleration fields are per tick). The runtime converts them to radians
  internally; do not pre-convert JSON values.

## Timing and Expressions (Hard Rules)

The editor has multiple kinds of edit box. A text box is not a universal formula
field; the Java record type and Codec decide the value type.

- **NumberProvider fields** accept a number, a typed provider object, or a
  `NumberExprParser` string such as `"phase_tick * 0.5"`, `"$i * 15"`, or
  `"rand(0.6, 1.0)"`. Typical fields are danmaku count/speed/spread, both emitters' lifetime,
  angle/elevation, danmaku base_scale, and laser length/thickness; shooter count/speed and angle
  fields; origin offsets, aim angles, group rotation, and color-animation
  parameters; `delay.delay_ticks`; `set_variable.value`; `spellcard_init`
  health and duration; `caster_moves.x/y/z`; `compare.left/right`,
  `dynamic_tick_interval.period/offset`; and numeric mover parameters. They are
  evaluated whenever the owning action, condition, or mover config is used.
  `fire_danmaku.base_scale` and `fire_laser.thickness` are mixed-timing exceptions:
  the action resolves an initial value at spawn, then a nonconstant provider is
  re-evaluated by the projectile entity each flight tick (using its supported
  entity-provider subset).
  `repeat.count` and `fire_spell.duration` are also NumberProviders; a repeat
  count is resolved when the repeat action executes, while each nested action
  runs with its own current context.
- **Plain numeric fields** accept only ordinary JSON numbers. This includes
  `tick_interval.interval/offset`, `tick_elapsed.ticks`, `burst.waves/interval`,
  `trail_interval`, laser `setup_prepare/setup_start/setup_end`, shooter
  `health/damage/lifetime/ysm_duration`, `random_chance.probability`,
  `fire_laser.delayed_v0/delayed_v1`, `show_spell_title.duration/radius`,
  `set_spell_circle.size`, `play_sound.volume/pitch`, difficulty/flag fields,
  `add_variable.delta`, and `bounce_source` fields (`max_bounces`, factors,
  tangent offsets, `output_speed`, `retarget`). Do not put an expression string
  in these fields.
- **FormulaExpr fields** are strings only: `formula.x/y/z`, `orbital.radius/drift`,
  and `translate.x/y/z`. They describe the projectile trajectory and are
  evaluated every flight tick. `$variables`, `phase_tick`, and `total_tick` are
  substituted into the formula at mover creation, not read live afterwards.
  In `translate` formula mode, target and origin coordinates are snapshotted;
  caster coordinates can follow the live owner position when owner data exists.
  For `formula`, `x/y/z` are forward/right/up offsets and the conceptual path is
  `origin + baseDirection * formula.speed * tick + forward*x(tick) + right*y(tick) + up*z(tick)`.
  `translate.speed` + `aim` resolves a fixed direction at creation; `homing` is
  the mover for live-target steering. FormulaExpr and NumberProvider are
  separate parsers, even though both are entered through an edit box.
  In a normal action/condition NumberProvider, `tick` is the current phase tick;
  in the projectile entity's mixed visual-scale evaluator, `tick` is the
  projectile age. In FormulaExpr mover strings, `tick`/`t`/`bullet_tick` are
  always the projectile flight tick.
- Use the field types and timing described in the bundled reference below. A label or a neighboring field does not make an ordinary number into an expression.

`on_enter` runs once at phase entry. `on_tick` runs once per phase tick; a
`spawn_shooter.body` runs once per shooter tick. `on_damage` is event-driven.
`delay` schedules its body once (the queued action is keyed to spell total time
and can still execute after a phase transition), while `conditional` re-tests
its condition each time it is reached. Projectile `on_trail` runs at `trail_interval`,
`on_hit_entity`/`on_hit_block` run only on the matching collision, and
`on_expiry` runs at expiration or when a hit behavior is `expire`.

Hit-control actions are callback-only for `fire_danmaku` projectiles. The
current laser callback path does not propagate mutable hit disposition back to
the laser entity, so do not use hit-control actions in `fire_laser.on_hit_*`.
`bounce_source` (the canonical exported
name; `bounce` is accepted as a decode alias) reflects the current danmaku from
a block surface and may be used only in `on_hit_block`. `continue_source`,
`expire_source`, and `discard_source` resolve the current hit as pass-through,
expire-with-callback, or erase-without-callback respectively; they may be used
in either hit callback. `hold_source` pins the current projectile at the hit
point for its `duration` ticks, then executes `on_release` with the same hit
context. Do not put these actions in `on_tick`, `on_expiry`, `on_trail`, or a
generic `delay` body: they would have no hit context. Keep one terminal
hit-control action per callback; the callback runner stops after a disposition
is resolved.

`hit_behavior_entity` and `hit_behavior_block` remain fallback policies
(`discard`, `expire`, `continue`) when the callback leaves the hit unresolved.
Bounce is not a fourth `hit_behavior` value. After `max_bounces` is exhausted,
the runtime falls back to `hit_behavior_block` for the next collision. The
`on_hit_block` callback can therefore execute up to `max_bounces + 1` times per
projectile; keep callback bodies cheap and account for that fan-out in dense
patterns.

`tick_interval` is periodic: `phase_tick % interval == offset`. `offset` is a
modulo residue (`0 <= offset < interval`), never an absolute timeline value.
`dynamic_tick_interval` applies the same modulo test after casting its provider
results to integers; prefer integer-valued providers for stable phase alignment.
For a one-shot event use `delay` from `on_enter`, or compare
`phase_tick == N` in `on_tick`. `tick_elapsed` is level-triggered (`>= N`), so
combine it with `tick_interval` when a periodic stream should start later.
Never put `offset` under a generic `conditional` object or use an oversized
interval as a hidden one-shot switch.

## Tuning and targeted edits

For an existing card, start from `current_json`. Find the requested phase and action
list (`on_enter`, `on_tick`, `on_exit`, `on_damage`) and change only the relevant
structures. Preserve optional fields, IDs, and `custom_names` unless the edit changes
their meaning. Keep simple NumberProvider shorthand as strings; typed providers are
useful for constructs that shorthand cannot express.

Estimate overlapping waves and callback fan-out when tuning density. A pattern with
24 bullets every 20 ticks and 80-tick lifetime can keep about 96 main bullets alive
before secondary emitters. Use spacing, acceleration, and pauses to create rhythm;
reduce decorative trails or repeated callback emissions before losing the main shape.
The preview and play test establish readability; Codec acceptance alone does not.

For a Touhou recreation, use supplied observations or a measured ECL trace. Without
a trace, make a coherent visual interpretation and describe that limit when reporting
file work; the in-game response itself remains JSON only. Fit the actual trajectories,
not just colors and counts. Exponential deceleration is different from linear slowing.

## NumberProvider

NumberProvider fields accept a bare JSON number, a `NumberExprParser` shorthand string, or a typed object:

```json
12
"tick * 3"
"$i * 15"
"rand(0.6, 1.0)"
{ "type": "random", "min": 0.6, "max": 1.0 }
{ "type": "variable", "key": "i" }
{ "type": "phase_tick" }
{ "type": "add", "a": { "type": "variable", "key": "i" }, "b": 10 }
```

Shorthand grammar supports numbers, `$variable`, parentheses, unary `-`, `+`, `-`, `*`, `/`, `%`, functions `rand/random`, `lerp/lerp_time`, `hp/health/by_health`, `tick_mod`, `sin_deg`, `cos_deg`, `sin_rad`, `cos_rad`, `sqrt`, `abs`, `floor`, `ceil`, `round`, `pow`, `root`, `log/ln`, `exp`, `max`, `min`, `clamp`, `gaussian`, `choose`, and bare keywords `tick`/`phase_tick`, `total_tick`, `distance`, `target_height`, `game_difficulty`, `caster_x/y/z`, `caster_max_health`, `caster_power`, `target_x/y/z`, `target_fly_time`, `target_speed`.

Important: trig functions are explicit. Use `sin_deg`/`cos_deg` for degree input and `sin_rad`/`cos_rad` for radian input. Do not write bare `sin`/`cos` in NumberProvider shorthand or mover formulas.

Supported types:

- `constant`: `value`
- `random`: `min`, `max`
- `gaussian`: `mean` optional default `0`, `std_dev`
- `random_choice`: `values`
- `indexed`: `index`, `values`
- `lerp_time`: `start`, `end`, `duration`
- `by_health`: `at_full`, `at_empty`
- `tick_mod`: `period`
- `variable`: `key`
- `phase_tick`, `total_tick`, `distance`, `caster_x`, `caster_y`, `caster_z`, `caster_max_health`, `caster_power`, `target_x`, `target_y`, `target_z`, `target_height`, `game_difficulty`, `target_fly_time`, `target_speed`
- Math: `sin_deg`, `cos_deg`, `sin_rad`, `cos_rad` (`input`, optional `amplitude`, `phase`), `add`, `mul`, `div`, `mod`, `sqrt`, `abs`, `floor`, `ceil`, `round`, `pow` (`base`, `exponent`), `root` (`value`, `degree`), `log`, `exp`, `max`, `min`, `clamp`
- `conditional`: `condition`, `if_true`, `if_false`

Use typed provider JSON when the shorthand parser cannot express the structure clearly, especially for `conditional`. Mover formulas are different; their formula fields are strings parsed by `FormulaExpr`, not NumberProvider objects.

Codec detail: fields inside the `random`, `lerp_time`, `by_health`, `tick_mod`,
`gaussian`, and `random_choice` provider objects are literal numbers
(with `lerp_time.duration` and `tick_mod.period` as integers). Dynamic values
belong in the outer NumberProvider expression, for example
`{"type":"mul","a":{"type":"phase_tick"},"b":0.1}`, rather than nested
inside a `random.min` or `lerp_time.start` field. For `indexed`, `index` is a NumberProvider and `values` is a plain number array.

### Expression fields and evaluation timing

The editor uses several kinds of edit box. A text box does not by itself imply
that every value is an expression. The Java field type and its Codec decide what
is legal:

| Field family | JSON value | Parser and evaluation |
|---|---|---|
| NumberProvider | number, expression string, or typed provider object | `NumberExprParser`; evaluated whenever the owning action/condition/mover config reads it |
| Plain integer/float/double | JSON number only | Java primitive Codec; parsed once when the action/condition is created |
| FormulaExpr | string only | `FormulaExpr`; mover trajectory strings are evaluated every projectile flight tick, after context variables are bound at spawn |
| Plain string/enum | string | no arithmetic evaluation |

Typical NumberProvider edit boxes include `fire_danmaku` count/speed and both emitters' lifetime, angle, elevation, visual scale and laser length; `spawn_shooter`
count, speed and angle fields; origin offsets, aim angles, group rotation and
color-animation parameters; `delay.delay_ticks`; `set_variable.value`;
`set_spell_health.health`/`duration`; `caster_moves.x/y/z`;
`compare.left/right`, `dynamic_tick_interval.period/offset`; and the numeric
fields of acceleration, polar, Bezier, composite, layered, and homing movers.
`repeat.count` and `fire_spell.duration` are NumberProviders too. A repeat count
is resolved when the repeat action executes, and each nested action then reads
its own current context.
These accept expressions such as `"phase_tick * 0.5"` or `"$i * 15"` and are
evaluated when their owning action/condition executes or when a mover config is
created. A projectile stores the resolved
fire parameters; later phase ticks do not retroactively change that projectile's
count, speed, or lifetime.
In ordinary action/condition evaluation, the shorthand keyword `tick` aliases
the current `phase_tick`. For the projectile entity's mixed visual-scale
evaluator, `tick` instead means projectile age.

Visual scale is a deliberate mixed-timing exception: nonconstant
`fire_danmaku.base_scale` and `fire_laser.thickness` providers are evaluated once for
their spawn value and then re-evaluated by the projectile entity every flight
tick. That entity evaluator supports the arithmetic, time, trigonometric, random,
and interpolation provider variants implemented in
`EntityNumberProviderEvaluator`; context-dependent providers such as a runtime
`variable` fall back to the spawn value there.

Important plain-value fields include `tick_interval.interval/offset`,
`tick_elapsed.ticks`, `burst.waves/interval`, `trail_interval`, laser
`setup_prepare/setup_start/setup_end`, `spawn_shooter.health/damage/lifetime/ysm_duration`,
`random_chance.probability`, `fire_laser.delayed_v0/delayed_v1`,
`show_spell_title.duration/radius`, `set_spell_circle.size`,
`play_sound.volume/pitch`, difficulty/flag fields, and `add_variable.delta`.
An expression string in these fields is not a formula; it fails the Codec.

FormulaExpr fields are the string fields of `formula` (`x/y/z`), `orbital`
(`radius/drift`), and `translate` (`x/y/z`). They describe motion during flight,
not merely launch setup. `formula` and `orbital` re-evaluate the trajectory
formula each projectile tick. `translate` formula axes also re-evaluate each
tick; its `speed` + `aim` shorthand instead resolves a fixed direction at
creation. In all three movers, `$variables`, `phase_tick`, and `total_tick` are
bound from the spell context when the mover is created, so those names are not
live phase variables afterwards. In translate formula mode, target and origin
coordinates are snapshotted at creation; caster coordinates may track the live
owner position when owner data is available. `homing` is the explicit live-target
mover. In FormulaExpr, `tick`, `t`, and `bullet_tick` always mean projectile
flight ticks, not the phase clock.

For `formula`, the local axes are `x=forward`, `y=right`, and `z=up` relative to
the projectile's launch direction. Conceptually its position is
`origin + baseDirection * speed * tick + forward*x(tick) + right*y(tick) + up*z(tick)`;
the mover returns the displacement from the previous position. Thus a formula
such as `"(0.4 + tick * 0.01) * tick"` describes the entire flight curve, not
just the velocity at birth. `formula.speed` is an additional drift along the
pattern base direction.

`FormulaExpr` and `NumberExprParser` are separate languages. A NumberProvider
expression cannot be placed in a FormulaExpr object field, and a FormulaExpr
string is not a substitute for a plain integer. Use explicit trig names in both
languages (`sin_deg`, `cos_deg`, `sin_rad`, `cos_rad`).

Use this field reference to choose a NumberProvider, FormulaExpr string, or plain value; field names alone do not determine expression support.

### Runtime execution order

`on_enter` runs once when a phase is entered. `on_tick` runs once per phase tick;
the body of a `spawn_shooter` runs once per shooter tick in that shooter's own
runtime. `on_damage` runs only for a damage event, and transitions are tested
after the current tick's actions. `conditional` tests its condition each time
the action is reached. A `delay` schedules its body once after the requested
delay against spell total time, so it can execute after a phase transition; it
is not a repeating timer.

Projectile callbacks have their own event clocks: `on_trail` runs at each
`trail_interval` during flight, `on_hit_entity`/`on_hit_block` run only for the
corresponding collision, and `on_expiry` runs when the projectile expires or a
hit behavior is `expire`. Callback NumberProviders are evaluated at callback
time. Trail callbacks receive a snapshot of the parent projectile's runtime
variables; `set_variable`/`add_variable` writes made by the callback persist.

### Hit control and bounce

The runtime registers the following callback actions for `fire_danmaku`
projectiles. `fire_laser` callbacks currently receive only position/direction;
their hit-control dispositions are not applied to the laser entity, so use
ordinary effects there (for example `run_command`) rather than these source
controls.

- `bounce_source` (decode alias `bounce`): block-surface reflection. It accepts
  only plain numeric fields: `max_bounces` (default `1`, sanitized to `0..64`),
  `normal_factor` (default `-1`, clamped to `[-5,0]`), `tangent_factor`
  (default `1`, clamped to `[-5,5]`), world-space tangent offsets X/Y/Z (each
  default `0`, clamped to `[-50,50]`), optional `output_speed` (clamped to
  `0..20`), and `retarget` (default `false`). A normal factor of `-1` is a
  specular reflection; `0` removes the normal component and slides along the
  surface. The tangent offset is projected onto the contacted surface before
  it is added. `bounce_source` is meaningful only in `on_hit_block`; it is not
  a `hit_behavior_block` enum value. The `on_hit_block` callback is invoked
  again on each subsequent wall contact, up to `max_bounces + 1` executions
  for that projectile; certification cost analysis accounts for this fan-out.
- `continue_source`, `expire_source`, and `discard_source`: zero-field
  terminal controls for either hit callback. They override the corresponding
  `hit_behavior_*` fallback. `expire_source` runs the projectile's
  `on_expiry`; `discard_source` removes it without that callback.
- `hold_source`: `duration` (NumberProvider, ticks) and required `on_release`
  action list. A positive duration installs a zero-speed hold at the contact
  point and schedules release; zero executes `on_release` immediately. The
  release list inherits the original block/entity hit context, so it can end
  with `bounce_source` (block only), `continue_source`, `expire_source`, or
  `discard_source`. It is distinct from `delay`, which only schedules actions
  and never freezes a projectile.

If no active `SpellRuntimeHost` is available when a positive-duration hold is
requested, the server fails safe by clearing the hold and removing the source
projectile rather than leaving it permanently frozen. After release, if the
release body does not resolve a disposition, the original `hit_behavior_*`
fallback is applied.

The callback runner stops after the first terminal disposition in the initial
`on_hit_*` list. Avoid competing terminal controls in one list; use a
`conditional` to choose exactly one. `hold_source.on_release` is a regular
action list, so it should likewise contain one final disposition.

## Control Actions

- `conditional`: `condition`, `if_true`, optional `if_false`.
- `sequence`: `actions`.
- `repeat`: `count`, optional `index_variable` default `i`, `body`. Child actions can read `{"type":"variable","key":"i"}`.
- `delay`: `delay_ticks`, `body`.
- `burst`: `waves`, optional `interval`, optional `wave_variable`, `body`.
- `spawn_shooter`: creates independent shooter emitters through the same pattern emitter model used by danmaku actions. Required fields: `count`, `speed`, `body`. Optional fields: `health` default `40`, `damage` default `4`, `lifetime` default `100`, `circle`, `origin`, `angle_offset`, `spread` default `360`, `elevation`, `pattern` default `ring`, `aim_mode` default `target`, `outer_count`, `tilt_angle`, `group_rotation`, `mover`, `ysm_model`, `ysm_texture`, `ysm_animation`, `ysm_duration`, `ysm_clear_target`. `count`, `speed`, `angle_offset`, `spread`, `elevation`, `outer_count`, and `tilt_angle` are NumberProvider fields; `health`, `lifetime`, and `ysm_duration` are plain integers. Do not use old `velocity_x`, `velocity_y`, or `velocity_z`; that legacy path has been removed. - `erase_enemy_danmaku`: optional `radius`, `sessions_only`.

- `force_phase`: `phase_id`, optional `clear_screen`.
- `force_spell`: `spell_id`, optional `clear_screen`.
- `fire_spell`: `spell_id`, optional `phase_id`, optional `duration`.
- `play_sound`: `sound`, optional `volume`, `pitch`.
- `run_command`: `mode` (`as_caster`, `console`, `non_cheat`), `command` string without leading slash. Example: `{ "type": "run_command", "mode": "as_caster", "command": "yhspell stop @s 32" }`. Optional `hit_context` is `default`, `as_hit_entity`, `at_entity_pos`, or `at_block_pos`; it is useful only from projectile trail/hit callbacks.
- `teleport`: `destination`, optional `play_sound`.
- `teleport_random`: optional `max_distance`, `min_distance_factor`, `distance_variance`, `attempts`, `upward_bias`, `play_sound`.
- `confine_target`: `max_distance`, optional `push_speed`.
- `set_entity_flag`: `flag`, optional `enable`.
- `set_invulnerable`: required `duration` NumberProvider; timed boss damage immunity, with no movement freeze.
- `freeze_on_tick`: required `duration` NumberProvider; pauses ordinary phase `on_tick`
  execution and its clock only. It does not disable Boss AI, navigation, `caster_moves`, or
  entity movement, so an invulnerable moving phase can combine both actions.
- `ysm_render`: optional `model`, `texture`, `animation`, `duration`, `clear`, `clear_target` for YSM render overrides.
- `bounce_source` (decode alias `bounce`), `continue_source`, `expire_source`,

  `fire_laser` callbacks.
- `show_spell_title`: optional `description`, `duration` (plain int), `radius` (plain double), and `presentation`. The displayed name comes from `display.name`; do not add a second `name` here. Preserve existing presentation fields when modifying.
- `show_spell_card`: optional plain `duration`, `radius`, `hand` (`left`/`right`/`random`), `offset_right/up/forward`, `held_scale`, `display_scale`, `hold_ticks`, `throw_ticks`, `float_ticks`; no health or timing initialization.

- `broken`: editor salvage placeholder with optional `original_type`, `raw`, and `error` strings. It never executes and must be repaired or removed before apply/export/certification.
- `disabled`: `inner`.
- `noop`: no fields besides `type`.

## Conditions

All conditions require `type`.

Common conditions:

- `tick_interval`: `interval`, optional `offset`
- `dynamic_tick_interval`: `period`, optional `offset`
- `tick_elapsed`: `ticks`
- `health_below`, `health_above`: `threshold` ratio
- `target_health_below`, `target_health_above`: `threshold` ratio
- `distance_above`, `distance_below`: `distance`
- `variable_check`: `key`, `op`, `value`
- `compare`: `left`, `op`, `right`
- `and`, `or`: `conditions`
- `not`: `condition`
- `always`: optional `value`
- `random_chance`: `probability` plain float 0.0-1.0 (not a NumberProvider; expression strings are rejected)
- `target_on_ground`, `target_is_flying`, `target_is_fallflying`
- `target_speed`: `threshold`, optional `op`
- `difficulty_equals`: `difficulty` plain integer 0-3 (`PEACEFUL`=0, `EASY`=1, `NORMAL`=2, `HARD`=3), not a string enum
- `difficulty_above`: `min_difficulty` plain integer 0-3 (same scale as `difficulty_equals`)
- `hit_count`: `count`
- `entity_trait`: `trait` (`is_lunatic`, `is_chaotic`, `is_abyssal`)
- `entity_flag`: `flag`
- `hit_entity_is_player`: zero-field condition; true only in an entity-hit
  callback whose actual hit entity is a `Player`.

Operators for checks: `=`, `==`, `!=`, `<`, `<=`, `>`, `>=`.

`tick_interval` is a periodic modulo test:

```text
phase_tick % interval == offset
```

`offset` is a residue and must be an integer in `0 <= offset < interval`.
It is not an absolute phase tick. `offset: 0` with `interval: 20` fires at
`0, 20, 40, ...`; `offset: 120` with `interval: 20` is invalid and never
matches. `dynamic_tick_interval` has the same modulo semantics (the runtime
casts provider results to integers), but its `period` and `offset` are
NumberProviders evaluated each condition test. Prefer integer-valued
expressions for stable phase alignment.

For one-shot timing, do not put an absolute time in `offset` and do not use a
huge interval as a hidden one-shot switch. Use a delayed body from `on_enter`:

```json
{ "type": "delay", "delay_ticks": 120, "body": [ { "type": "fire_danmaku", "bullet": "ball", "color": "red", "count": 1, "speed": 0.5, "lifetime": 40 } ] }
```

Or compare the phase clock directly from `on_tick`:

```json
{
  "type": "conditional",
  "condition": { "type": "compare", "left": { "type": "phase_tick" }, "op": "==", "right": 120 },
  "if_true": [{ "type": "fire_danmaku", "bullet": "ball", "color": "cyan", "count": 8, "speed": 0.4, "lifetime": 60 }]
}
```

`tick_elapsed` is level-triggered (`phase_tick >= ticks`), so it remains true
after the threshold. Combine it with `tick_interval` for a periodic stream that
starts later, for example `and(tick_interval(24, 12), tick_elapsed(132))`.

## Movers

All movers require `type`.

Useful movers:

```json
{ "type": "acceleration", "x": 0, "y": -0.03, "z": 0 }
{ "type": "acceleration", "x": 0.02, "y": 0, "z": 0, "space": "local", "terminal_vx": 1.2 }
{ "type": "acceleration", "x": "$i * 0.02", "y": 0, "z": "sin_rad(tick) * 0.01" }
{ "type": "deceleration", "factor": 0.06 }
{ "type": "rotate", "degrees_per_tick": 5 }
{ "type": "polar", "radius": 2, "angular_speed": 8 }
{ "type": "zero" }
{ "type": "translate", "speed": 0.2, "aim": "target" }
{ "type": "bezier", "cp1_forward": 5, "cp1_right": 3, "cp2_forward": 10, "cp2_right": -3, "end_forward": 15, "duration": 40 }
```

Complete mover types and fields:

- `acceleration`: `x`, `y`, `z` NumberProvider components, each optional
  default `0`; optional `terminal_vx`, `terminal_vy`, `terminal_vz` cap each
  axis after acceleration. `space` defaults to `world` (X=east, Y=up,
  Z=south); set `space: "local"` for FormulaMover-compatible axes
  X=forward, Y=right, Z=up. This replaced the old nested `acceleration` Vec3
  shape. Acceleration is implemented by `BoundedAccelerationMover`, so it can
  be rebased after a bounce while preserving its acceleration/terminal limits.
- `deceleration`: `factor` NumberProvider.
- `rotate`: `degrees_per_tick` NumberProvider (degrees/tick; converted to
  radians by the runtime).
- `polar`: `radius`, `radial_speed`, `radial_accel`, `initial_angle`,
  `angular_speed`, `angular_accel` NumberProvider fields. `initial_angle` is
  in degrees; angular speed/acceleration are degrees per tick (and per
  tick-squared respectively), converted to radians internally.
- `composite`: `segments` of `{ "duration": NumberProvider, "mover": mover }`.
- `layered`: `layers` array of movers.
- `zero`: no fields.
- `bezier`: `cp1_forward`, `cp1_right`, `cp1_up`, `cp2_forward`, `cp2_right`, `cp2_up`, `end_forward`, `end_right`, `end_up`, `duration` NumberProvider fields.
- `multi_bezier`: `segments` with the same Bezier segment fields.
- `spline`: `waypoints` as numeric arrays `[forward, right, up]`, optional `duration` NumberProvider, `closed`.
- `formula`: string formulas `x`, `y`, `z`, optional `speed` NumberProvider.
- `attached`, `attached_free_rot`: no fields.
- `fixed_dir`: `inner` mover.
- `orbital`: `angular_speed` NumberProvider in degrees/tick (converted to
  radians internally), string formulas `radius`, `drift`.
- `translate`: string formulas `x`, `y`, `z`, optional `speed` NumberProvider, `aim` (`none`, `target`, `caster_to_target`, `forward`, `velocity`, `fixed`). With `speed` and `aim="fixed"`, `x/y/z` are interpreted as a fixed direction vector.
- `homing`: `speed` NumberProvider (blocks/tick), optional `turn_rate` (degrees/tick) and `delay` (ticks). Steering follows the holder's live target.

Formula mover strings use `FormulaExpr`, not NumberProvider JSON. `FormulaExpr` trig functions also require explicit units: `sin_rad`, `cos_rad`, `sin_deg`, `cos_deg`; the `pi` constant is available. Common variables include `tick`, `t`, `bullet_tick`, `pi`, `e`, and functions `abs`, `sqrt`, `floor`, `ceil`, `round`, `log`/`ln`, `exp`, `min`, `max`, `pow`, `root`. `formula`, `orbital`, and `translate` string fields also bind `$variable`, `phase_tick`, and `total_tick` from the `SpellContext` at spawn time. `translate` rich formulas additionally expose `targetX/Y/Z` (`tx/ty/tz`), `casterX/Y/Z` (`cx/cy/cz`), `originX/Y/Z` (`ox/oy/oz`), `dist`, `dx`, `dy`, and `dz`.

Warning: unlike `NumberExprParser` (which rejects unknown names), `FormulaExpr` does NOT report unknown identifiers. A bare `sin`/`cos` token or any misspelled name silently evaluates to `0`, and a bad function call makes the whole formula fail to compile and return `null` (no motion), with no runtime error. `MoverConfigs` substitutes `$variable`, `phase_tick`, and `total_tick` at spawn time; these are not live per-tick variables. Always use `sin_deg`/`cos_deg`/`sin_rad`/`cos_rad` and double-check formula strings.

Choose movers from the observed trajectory instead of defaulting to speed-only
bullets. Use `polar` or `orbital` for rotating/radial rings, `bezier`,
`multi_bezier`, or `spline` for authored curves, `composite` for local-time
segments, `layered` for additive motion roles, `translate` for world-space
offsets or creation-time aim, `homing` for live-target steering, and `formula`
for measured per-tick curves. When a mover is present, `fire_danmaku.speed`
provides initial velocity/base-direction input and may not equal the visible
displacement; tune the mover's own speed, duration, or formula.

Bounce rebasing is mover-dependent. The current runtime can rebase
`BoundedAccelerationMover` (the `acceleration` config) at the contact point and
reset its local time; other movers (`formula`, `polar`, `orbital`, curves,
`translate`, `homing`, etc.) are detached on bounce and continue with the
resolved outgoing velocity as a speed-only projectile. `hold_source` preserves
the pre-hit mover while held, then uses the same rebase rule when released.

## Pattern Notes

- `ring`: evenly around 360 degrees; `count` bullets.
- `line`: fan spread using `spread`.
- `random`: random yaw inside `spread`; random elevation if `elevation` is nonzero.
- `aimed`: all bullets in the same direction.
- `nested_ring`: requires `outer_count`; total bullets are `outer_count * count`; `elevation` controls inner arc, `tilt_angle` controls inner plane.
- `grid`: `count` rows and `outer_count` columns.
- `sphere`: Fibonacci sphere; `count` total.
- `sphere_random`: random sphere points.
- `spiral`: angle sweep across `spread`.
- `cone`: `elevation` is cone half-angle around forward direction.


## Transitions and presentation

Transitions are objects with condition, target_phase, and optional mode
(immediate, clear_screen, clear_and_reset). Do not invent a to or next_phase field.
For a health-declared multi-segment card, use the init node's completion targets
consistently rather than unrelated forced phase switches.

NumberProviders also include target_facing_x/y/z and callback_value with a string key.
In a callback, shorthand such as source_speed, source_x/y/z, source_velocity_x/y/z,
source_direction_x/y/z, source_age, source_lifetime, source_remaining_lifetime,
source_size, source_spread, hook_x/y/z, hit_x/y/z, hit_normal_x/y/z,
laser_start_x/y/z, source_end_x/y/z, and source_clipped_end_x/y/z reads that callback's
snapshot. Equivalent typed form: {"type":"callback_value","key":"source_speed"}.
Use source_direction aim to retain the emitting projectile's direction in a callback.

Optional ysm_projectile presentation applies to any current bullet and lasers.
Fields are model_source="fixed", model (existing model name), slot, model_scale,
max_instances, fallback="yh", acknowledge_cost, offset_forward/right/up,
pitch_offset, yaw_offset, and tilt_offset. All numeric fields here are plain JSON
numbers. Preserve the player's model selection, cost acknowledgement, and limits;
this is optional appearance, not a way to define new bullet enums or physical behavior.
play_sound also accepts plain source (a Minecraft sound category), origin
(caster/target/action/hit), radius, and attenuation. These are not NumberProviders.

spawn_shooter also supports the current nested `ysm` presentation object, plain
`targetable` and `random_axis` booleans, and a `base_scale` NumberProvider. Legacy
`ysm_model`/`ysm_texture`/`ysm_animation`/`ysm_duration`/`ysm_clear_target` remain
readable; preserve a current editor export's nested presentation when modifying it.
